01

Rôles, fonctionnalités, Desktop ou Core

Windows Server est une base neutre qu'on spécialise : un rôle dit ce que fait le serveur (contrôleur de domaine, DHCP, serveur web), une fonctionnalité lui ajoute une brique de support (outils d'administration, sauvegarde, clustering).

Ce que tu sauras faire

  • Distinguer un rôle d'une fonctionnalité et donner un exemple de chacun.
  • Choisir entre Desktop Experience et Server Core selon l'usage du serveur, et justifier.
  • Installer, lister et retirer un rôle avec Install-WindowsFeature, Get-WindowsFeature et Uninstall-WindowsFeature.

Avant de commencer : module Hyper-V (une VM Windows Server du lab) · 30 min · une session PowerShell ouverte en administrateur.

Un même Windows pour des métiers très différents

Le service demande un serveur DHCP pour les postes. On n'installe pas un autre système : on ajoute un rôle à un Windows Server existant. Dans le lab Orion, SRV-AD01 est à la fois contrôleur de domaine, serveur DNS et serveur DHCP, et SRV-FILE01 ne fait que des partages : même système, rôles différents.

Savoir ce qu'on installe, et ce qu'on laisse de côté, évite un serveur chargé de services inutiles à mettre à jour et à protéger.

Rôle, fonctionnalité et édition d'installation

Un rôle répond à la question « que fait ce serveur ? » ; une fonctionnalité répond à « de quelle brique de support a-t-il besoin pour le faire ou pour être administré ? ». Par-dessus, l'édition d'installation décide s'il y a un bureau ou non.

NotionQuestion à se poserExemples
RôleQue fait le serveur ?AD DS (contrôleur de domaine), DNS, DHCP, serveur web (Web-Server)
FonctionnalitéQuelle brique lui ajoute-t-on ?Outils d'administration, sauvegarde, clustering
Édition d'installationA-t-il un bureau ?Desktop Experience ou Server Core

Desktop Experience

Interface graphique complète. Plus simple à apprendre et à administrer localement, mais plus de composants à mettre à jour et une surface d'attaque plus grande. C'est l'édition utilisée dans le lab.

Server Core

Pas de bureau : administration en PowerShell, avec sconfig pour les réglages de base, ou à distance (Server Manager, Windows Admin Center). Moins de mises à jour, moins de failles. Le bon choix pour un DC ou un DNS en production.

Source : Microsoft Learn — What is the Server Core installation option in Windows Server · Microsoft Learn — Install-WindowsFeature

Exemple travaillé

Préparer SRV-AD01 : quelle édition, quels rôles, dans quel ordre ?

  1. Étape 1 · le besoin

    Un premier serveur qui porte l'annuaire, le DNS et le DHCP

    Le lab a besoin d'un contrôleur de domaine (rôle AD DS), d'un DNS et d'un DHCP pour les postes. Ce sont trois rôles sur la même machine, SRV-AD01.

  2. Étape 2 · l'édition

    Desktop Experience pour apprendre, Core pour la production

    On apprend avec les consoles graphiques sous les yeux : le lab utilise Desktop Experience. En production, un DC ou un DNS gagne à passer en Server Core (moins de mises à jour, moins de failles), administré à distance.

  3. Étape 3 · l'installation

    Rôle, consoles, redémarrage annoncé

    Chaque rôle s'installe avec -IncludeManagementTools pour avoir ses consoles ; le redémarrage n'est demandé (-Restart) que quand on est prêt et qu'on l'a annoncé.

    Le serveur fait ce qu'on lui a demandé et rien de plus : chaque rôle installé a une raison d'être.

PowerShell — rôles et fonctionnalités
Get-WindowsFeature | Where-Object Installed            # ce qui est installé
Install-WindowsFeature DHCP -IncludeManagementTools      # rôle + ses consoles
Uninstall-WindowsFeature Web-Server -Remove              # -Remove supprime aussi les fichiers

Le redémarrage, quand on veut

Dans l'assistant du Server Manager comme en PowerShell, on ne coche pas « redémarrer automatiquement » : on garde la main sur le moment du redémarrage, et on l'annonce. -Restart seulement quand on est prêt.

Vérifier

Dans le terminal ci-dessus, lance Get-WindowsFeature | Where-Object Installed : la liste ne montre que ce qui est installé, chaque ligne avec son nom court (celui à passer à Install-WindowsFeature). Après l'installation d'un rôle, il doit y figurer ; après Uninstall-WindowsFeature, il doit en avoir disparu.

Le rôle est listé mais sa console n'apparaît pas dans le menu Outils du Server Manager : il a été installé sans -IncludeManagementTools.

À toi — installer un rôle avec ses consoles

Sur un serveur du lab, installe le rôle DHCP avec ses outils d'administration, sans redémarrer automatiquement. Énoncé seul : écris la commande.

Voir la solution
PowerShell

Pas de -Restart : on garde la main sur le moment du redémarrage.

Variante sans indice

Le rôle serveur web (Web-Server) n'a plus d'utilité sur un serveur. Retire-le en supprimant aussi ses fichiers.

Voir la solution
PowerShell
Uninstall-WindowsFeature Web-Server -Remove

C'est -Remove qui supprime aussi les fichiers du rôle ; sans lui, ils restent sur le disque.

Quand ça casse — la console DHCP manque à l'appel

Sur SRV-AD01, Get-WindowsFeature montre que le rôle DHCP est installé, mais la console DHCP n'apparaît pas dans le menu Outils du Server Manager.

Voir la démarche et la cause

Démarche : le rôle est bien là, c'est donc son outil d'administration qui manque. Cause : le rôle a été installé sans -IncludeManagementTools. Correctif : relancer Install-WindowsFeature DHCP -IncludeManagementTools (reconstitué, non testé : le module ne montre que l'installation initiale), puis rouvrir le Server Manager.

À retenir

  • Rôle = ce que fait le serveur ; fonctionnalité = ce qui l'aide à le faire.
  • Install-WindowsFeature … -IncludeManagementTools installe le rôle et ses consoles ; -Remove supprime aussi les fichiers au retrait.
  • Desktop Experience pour apprendre, Server Core pour la production quand c'est possible.

02

Préparer les serveurs du lab

Tous les serveurs du lab partent du même disque parent généralisé par Sysprep (module Hyper-V), puis reçoivent leur identité réseau. L'ordre compte : adresse et DNS d'abord, nom ensuite, domaine en dernier.

Ce que tu sauras faire

  • Donner à un serveur son identité réseau dans le bon ordre : adresse, DNS, nom, domaine.
  • Expliquer pourquoi un membre de domaine n'utilise que le DNS des contrôleurs de domaine.
  • Vérifier avec Get-NetIPConfiguration et Resolve-DnsName qu'un serveur est prêt à rejoindre le domaine.

Avant de commencer : chapitre Rôles, fonctionnalités, Desktop ou Core et module Hyper-V (disque parent Sysprep) · 35 min · une VM du lab démarrée sur le commutateur LABOPS.

Un serveur qu'on ne retrouve pas ne sert à personne

Un serveur issu d'un disque parent généralisé n'a ni adresse fixe ni nom utile : tous les clones se ressemblent. Les postes, eux, doivent le joindre toujours au même endroit, et le serveur doit trouver le domaine pour s'y inscrire. Sans cette préparation, la jonction au domaine échoue, et c'est le DNS qu'on met en cause bien après coup.

Dans le lab Orion, chaque serveur prend son adresse dans le plan d'adressage : un petit script de premier démarrage, toujours le même, évite les oublis.

Pourquoi l'ordre adresse, DNS, nom, domaine

Chaque étape prépare la suivante. Un serveur ne peut pas joindre un contrôleur de domaine s'il n'a pas d'adresse ; il ne le trouve que si son DNS connaît le domaine, parce que le DC se découvre par des enregistrements SRV publiés dans la zone DNS du domaine ; le nom est mieux choisi avant d'entrer dans l'annuaire, où il devient un objet.

2. DNSLes DC seulement (172.16.50.10)Seul le DNS du domaine connaît ses enregistrements SRV
3. NomNom du serveur, puis redémarrageRenommer après la jonction ou la promotion est possible, mais plus délicat
4. DomaineJonction au domaine, puis redémarrageLes trois étapes précédentes sont en place

Source : Microsoft Learn — Set-DnsClientServerAddress · Microsoft Learn — Add-Computer

Exemple travaillé

SRV-AD01 démarre pour la première fois depuis le disque parent

  1. Étape 1 · l'adresse

    Le plan Orion donne 172.16.50.10

    On repère le nom de la carte avec Get-NetAdapter, puis on fixe l'adresse, le préfixe /24 et la passerelle 172.16.50.1 (l'hôte Hyper-V).

  2. Étape 2 · le DNS

    Le premier DC pointe vers lui-même

    SRV-AD01 sera le premier DNS du domaine : il se déclare lui-même comme serveur DNS (172.16.50.10). Les autres serveurs pointeront vers lui.

  3. Étape 3 · le nom

    Un nom lisible, un redémarrage

    On renomme en SRV-AD01 avec -Restart : il n'y a pas encore de domaine à joindre, puisque c'est lui qui va le créer (chapitre suivant).

    Pour SRV-AD02 ou SRV-FILE01, la dernière étape est Add-Computer -DomainName orion.local -Restart, avec le DNS déjà pointé vers 172.16.50.10.

PowerShell — SRV-AD01 au premier démarrage (script du TP final)
Get-NetAdapter                                          # repérer le nom de la carte
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 172.16.50.10 -PrefixLength 24 -DefaultGateway 172.16.50.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 172.16.50.10
Disable-NetAdapterBinding -Name "Ethernet" -ComponentID ms_tcpip6   # IPv6 coupé dans le lab
Rename-Computer -NewName "SRV-AD01" -Restart

Les membres du domaine (SRV-AD02, SRV-FILE01…) prennent le même schéma avec leur adresse du plan Orion, et pointent leur DNS vers 172.16.50.10 avant de joindre le domaine : Add-Computer -DomainName orion.local -Restart.

Le piège du DNS public

Le TP DNS du cours fait volontairement partir les serveurs avec 8.8.8.8 en DNS, puis fait corriger. À retenir : un membre de domaine n'utilise que le DNS des contrôleurs de domaine. Avec un DNS public, ni la jonction au domaine ni l'ouverture de session ne fonctionnent.

Vérifier

Le serveur est-il prêt à rejoindre le domaine ?

PowerShell
Get-NetIPConfiguration
Resolve-DnsName orion.local            # une fois SRV-AD01 promu

Sortie attendue

InterfaceAlias       : Ethernet
IPv4Address          : 172.16.50.20
IPv4DefaultGateway   : 172.16.50.1
DNSServer            : 172.16.50.10

Add-Computer répond « The specified domain either does not exist or could not be contacted » (erreur 1355) : c'est souvent le DNS du serveur, pas le domaine.

À toi — préparer SRV-FILE01

SRV-FILE01 doit prendre l'adresse 172.16.50.20/24 du plan Orion, avec sa passerelle, et n'utiliser que le DNS du premier contrôleur de domaine. Énoncé seul : écris les deux commandes (la carte s'appelle Ethernet).

Voir la solution
PowerShell — SRV-FILE01
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 172.16.50.20 -PrefixLength 24 -DefaultGateway 172.16.50.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 172.16.50.10

Mêmes commandes que pour SRV-AD01, avec l'adresse de SRV-FILE01 (reconstitué, non testé). Le DNS reste 172.16.50.10, jamais 8.8.8.8.

Variante sans indice

Tu prépares un nouveau serveur : tu as son adresse, son DNS, son nom et la jonction au domaine à faire. Dans quel ordre fais-tu les quatre opérations, et pourquoi la jonction passe-t-elle en dernier ?

Voir la solution

Adresse, DNS, nom, puis domaine. La jonction vient en dernier parce qu'elle a besoin d'une adresse qui joint le contrôleur de domaine et d'un DNS qui connaît orion.local ; le nom se choisit avant que le serveur devienne un objet de l'annuaire.

Quand ça casse — le domaine reste introuvable

Depuis SRV-FILE01, ping 172.16.50.10 répond. Pourtant Resolve-DnsName orion.local échoue, et Add-Computer répond « The specified domain either does not exist or could not be contacted ».

Voir la démarche et la cause

Démarche : le ping par adresse répond, le réseau et la passerelle fonctionnent ; c'est donc la résolution du nom qui échoue. Lire la ligne DNSServer de Get-NetIPConfiguration. Cause : le serveur interroge un DNS public (par exemple 8.8.8.8), qui ne connaît ni orion.local ni ses enregistrements SRV. Correctif : Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 172.16.50.10, puis Resolve-DnsName orion.local pour confirmer.

Question éclair

SRV-FILE01 a l'adresse 172.16.50.20, la passerelle .1 et le DNS 8.8.8.8. ping 172.16.50.10 répond, mais Add-Computer -DomainName orion.local échoue. Que corriges-tu ?

Le ping par adresse prouve que le réseau marche. Pour joindre le domaine, le serveur doit trouver un DC par les enregistrements SRV de orion.local : seul le DNS du domaine les connaît. Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 172.16.50.10, puis Resolve-DnsName orion.local pour vérifier.

À retenir

  • Adresse fixe, DNS vers les DC, nom, puis domaine — dans cet ordre.
  • Un membre de domaine n'utilise que le DNS des contrôleurs de domaine : un DNS public ne connaît pas orion.local.
  • Avant la jonction, Get-NetIPConfiguration et Resolve-DnsName orion.local disent si le serveur est prêt. Renommer après coup reste possible, mais plus délicat.

03

Active Directory : la forêt et le premier contrôleur

AD DS est l'annuaire du réseau : il authentifie les utilisateurs, organise les machines et distribue les stratégies. Tout part d'une forêt qui contient un domaine, et d'un premier contrôleur de domaine (DC).

Ce que tu sauras faire

  • Décrire forêt, domaine, contrôleur de domaine, OU et site, et les situer dans le lab Orion.
  • Promouvoir le premier contrôleur de domaine avec Install-ADDSForest.
  • Expliquer pourquoi AD dépend du DNS et des enregistrements SRV.
  • Contrôler le résultat avec Get-ADDomain, dcdiag et Resolve-DnsName, et lire les niveaux fonctionnels.

Avant de commencer : chapitre Préparer les serveurs du lab (SRV-AD01 a son adresse 172.16.50.10 et son nom) · 40 min · une VM Windows Server du lab.

Un seul annuaire plutôt qu'un compte par machine

Sans annuaire, chaque poste garde ses propres comptes : créer un utilisateur, le désactiver, changer une règle de sécurité se fait machine par machine. Avec AD DS, l'identité est centralisée : on crée un compte une fois, il ouvre une session partout, et une stratégie posée une fois s'applique à tout un service.

Ce service tient en un point : le contrôleur de domaine. Le monter proprement, avec le DNS dont il dépend, est donc la première étape de tout le reste du module.

La promotion fixe aussi les niveaux fonctionnels de la forêt et du domaine (paramètres -ForestMode et -DomainMode) : ils décident des fonctions d'AD disponibles et de la version minimale de Windows des DC. Windows Server 2025 apporte son propre niveau (Windows Server 2025). Dans l'autre sens, pour ajouter un DC 2025 à une forêt existante, celle-ci doit être au moins au niveau Windows Server 2016. Le niveau se lit avec (Get-ADForest).ForestMode et (Get-ADDomain).DomainMode. On le monte une fois tous les DC à jour ; le redescendre n'est possible que dans des cas limités.

La promotion installe le DNS (par défaut pour une nouvelle forêt) et crée la zone DNS orion.local intégrée à l'annuaire, avec les enregistrements SRV (_ldap._tcp, _kerberos._tcp) par lesquels les postes trouvent leurs contrôleurs. C'est pour ça qu'AD ne fonctionne pas sans un DNS correct.

Source : Microsoft Learn — Active Directory Domain Services overview · Microsoft Learn — Install-ADDSForest

Exemple travaillé

Ce que fait la promotion de SRV-AD01, pas à pas

  1. Étape 1 · les paramètres

    Un nom de domaine DNS et son nom court

    -DomainName "orion.local" donne l'espace de noms ; -DomainNetbiosName "ORION" le nom court. La commande demande ensuite un mot de passe DSRM, pour restaurer l'annuaire en cas de panne, puis une confirmation.

  2. Étape 2 · ce qui est créé

    Forêt, domaine, DNS et zone intégrée

    Avec -InstallDns, le serveur devient aussi serveur DNS, avec la zone orion.local intégrée à l'annuaire et ses enregistrements SRV (_ldap._tcp, _kerberos._tcp).

  3. Étape 3 · après le redémarrage

    Les postes peuvent trouver un DC

    Un poste dont le DNS pointe vers SRV-AD01 interroge ces enregistrements SRV pour trouver un contrôleur de domaine. C'est aussi ce qu'on vérifie juste après.

    Un seul DC, une seule forêt : le second DC (chapitre suivant) viendra supprimer ce point de panne.

PowerShell — SRV-AD01
Install-WindowsFeature AD-Domain-Services, DNS -IncludeManagementTools
Install-ADDSForest -DomainName "orion.local" -DomainNetbiosName "ORION" -InstallDns
# demande le mot de passe DSRM (restauration de l'annuaire), une confirmation, puis redémarre

Vérifier

Le domaine répond-il, et le contrôleur est-il sain ?

Get-ADDomain | Select-Object DNSRoot, NetBIOSName, PDCEmulator

Quand ça casse — dcdiag proteste juste après la promotion

SRV-AD01 vient de redémarrer après Install-ADDSForest. Tu lances dcdiag /q tout de suite : il affiche des erreurs sur les tests DNS et Advertising.

Voir la démarche et la cause

Démarche : noter depuis quand le serveur a redémarré, puis relire le résultat plus tard avant de toucher à quoi que ce soit. Cause probable : un service pas encore démarré juste après la promotion. Correctif : attendre quelques minutes et relancer dcdiag /q ; s'il se tait, tout va bien. Si l'erreur persiste, contrôler que Resolve-DnsName _ldap._tcp.orion.local -Type SRV répond.

À retenir

  • Install-ADDSForest crée forêt, domaine et DNS intégré en une commande ; le mot de passe DSRM sert à restaurer l'annuaire.
  • Les enregistrements SRV publiés dans le DNS permettent aux postes de trouver un DC : sans DNS, pas d'AD.
  • dcdiag /q n'affiche rien quand tout va bien ; juste après la promotion, patienter avant de conclure à une panne.

04

Le second contrôleur de domaine, par IFM

Un seul DC, c'est un seul point de panne pour toute l'authentification. Le TP final impose un second DC, promu à partir d'un IFM (Install From Media) : une copie de l'annuaire préparée sur le premier, qui évite de tout répliquer par le réseau.

Ce que tu sauras faire

  • Expliquer pourquoi un domaine a au moins deux contrôleurs et ce qu'apporte l'IFM.
  • Promouvoir SRV-AD02 à partir d'un média créé sur SRV-AD01.
  • Nommer les cinq rôles FSMO et dire lequel se remarque en premier quand il s'arrête.
  • Contrôler la réplication avec repadmin /replsummary et lister les rôles avec netdom query fsmo.

Avant de commencer : chapitres Active Directory : la forêt et le premier contrôleur et Préparer les serveurs du lab · 40 min · SRV-AD01 promu, SRV-AD02 membre du domaine (172.16.50.11).

Quand l'unique contrôleur s'arrête, tout s'arrête

Avec un seul DC, une panne ou une maintenance de SRV-AD01 prive tout le domaine d'authentification et de DNS. Un second DC règle ce point de panne : il porte une copie complète de l'annuaire, du DNS et du catalogue global, et prend le relais.

Le TP final impose ce second DC. On le promeut avec un média (IFM) plutôt que par réplication complète sur le réseau : c'est la méthode qu'on utilise quand le lien vers le site est lent.

L'IFM : promouvoir un DC à partir d'une copie locale

L'IFM (Install From Media) est une copie de l'annuaire préparée sur le premier DC, qu'on emporte sur le futur DC : la promotion lit cette copie au lieu de tout recevoir par le réseau, puis la réplication ne transfère que ce qui a changé depuis la création du média.

Sur un petit lab, l'IFM ne fait gagner que quelques secondes ; sur un site distant relié par un lien lent, il évite de faire transiter des gigaoctets. La réplication ne transfère ensuite que ce qui a changé depuis la création du média.

Les rôles FSMO

Tous les DC sont égaux pour authentifier, mais cinq opérations n'ont qu'un seul maître : les rôles FSMO. Le premier DC les porte tous. Le plus sollicité au quotidien est l'émulateur PDC : source de temps du domaine, référence pour les changements de mot de passe.

Exemple travaillé

Ajouter SRV-AD02 : de la copie de l'annuaire au second DC

  1. Étape 1 · le média

    Une copie de l'annuaire, créée sur SRV-AD01

À toi — SRV-AD01 part en maintenance une semaine

SRV-AD01 porte les cinq rôles FSMO et sera arrêté une semaine, mais il reviendra. SRV-AD02 est en ligne. Que fais-tu des rôles FSMO, et quelle commande te dit où ils sont ?

Voir la solution

Tu transfères les rôles avant l'arrêt, puisque le DC source est en ligne : Move-ADDirectoryServerOperationMasterRole. netdom query fsmo liste les porteurs, avant comme après. Pas de saisie (-Force) : l'ancien porteur n'est pas perdu.

Variante sans indice

Le disque de SRV-AD01 est détruit pour de bon ; le serveur ne reviendra jamais. SRV-AD02 est sain. Que fais-tu des rôles FSMO, et que ne dois-tu surtout pas faire ensuite avec l'ancien DC ?

Voir la solution

L'ancien porteur est perdu pour de bon : on saisit les rôles sur SRV-AD02 (-Force). L'ancien DC ne doit jamais revenir sur le réseau avec son ancien état : on le retire du domaine et on nettoie ses métadonnées.

Quand ça casse — la réplication échoue

Après la promotion de SRV-AD02, repadmin /replsummary affiche des échecs dans la colonne fails/total pour SRV-AD02, alors que tout semblait fonctionner la veille.

Voir la démarche et la cause

Démarche : lire le détail avec repadmin /showrepl, puis contrôler deux choses. Causes possibles : un DC ne se résout plus dans le DNS de l'autre, ou l'heure des deux DC diffère de plus de 5 minutes (Kerberos). Correctif : rétablir la résolution de nom entre les deux DC et remettre les horloges d'accord (l'émulateur PDC est la source de temps du domaine), puis relancer repadmin /replsummary.

Question éclair

SRV-AD01, qui porte les cinq rôles FSMO, est arrêté une heure pour maintenance. SRV-AD02 (DNS, catalogue global) tourne. Que se passe-t-il pour les utilisateurs ?

Un second DC sert justement à ça : il a toute la base, le DNS et le catalogue global. Pendant une heure, aucune opération à maître unique ne manque vraiment. Pour une absence longue, on transfère les rôles avant l'arrêt ; on ne les saisit que si SRV-AD01 ne reviendra jamais.

À retenir

  • Deux DC minimum ; l'IFM promeut le second à partir d'une copie locale de l'annuaire.
  • Cinq rôles FSMO, un seul maître chacun : on les transfère quand le DC source est en ligne, on ne les saisit que s'il est perdu pour de bon.
  • repadmin /replsummary doit afficher zéro échec ; l'émulateur PDC donne l'heure à tout le domaine.

Organiser l'annuaire : OU, groupes, comptes, délégation

Un annuaire bien rangé se reconnaît à trois choses : des OU qui suivent l'organisation, des droits donnés à des groupes (jamais à des personnes), et des tâches courantes déléguées sans donner les clés du domaine.

Ce que tu sauras faire

  • Ranger des comptes et des groupes dans des OU qui suivent l'organisation (New-ADOrganizationalUnit, New-ADGroup, New-ADUser).
  • Choisir l'étendue d'un groupe (globale, domaine local, universelle) et appliquer la règle AGDLP.
  • Déléguer la gestion des comptes d'une OU à un utilisateur sans en faire un administrateur du domaine.

Avant de commencer : chapitre Installer Active Directory (le domaine orion.local existe) · 35 min · une session PowerShell sur SRV-AD01.

Un annuaire plat devient ingérable

Quand l'entreprise grossit, un annuaire où tous les comptes se mélangent pose vite trois questions : à qui donner l'accès au dossier du service Development, qui a le droit de créer un compte, et que faire quand quelqu'un change de service ? Si chaque droit est donné à une personne, chaque arrivée et chaque départ obligent à repasser sur toutes les ressources.

Dans Orion, Sacha Somers rejoint le service Development : on veut un seul geste (l'ajouter à un groupe) et non vingt réglages, et on veut qu'un collègue puisse créer les comptes de ce service sans détenir les clés de tout le domaine.

OU, groupes et délégation : trois outils, trois rôles

Une OU range des objets (comptes, ordinateurs, groupes) selon l'organisation, et c'est sur elle qu'on applique des GPO ou qu'on délègue une tâche. Un groupe ne range rien : il porte des droits. On ne confond donc pas les deux : l'OU dit où l'objet vit, le groupe dit ce qu'il a le droit de faire. La délégation confie une tâche précise sur une OU (par exemple gérer les comptes) à un utilisateur ou à un groupe, sans en faire un administrateur du domaine.

Les étendues de groupes, et la règle AGDLP

ÉtendueContientSert à
GlobaleDes comptes et des groupes globaux du même domaineRegrouper des personnes par fonction (DEV-GRP)
Domaine localDes comptes, des groupes globaux et universels de toute la forêt (et des domaines approuvés), d'autres groupes de domaine local du même domainePorter des droits sur une ressource (DL-DEV-Modif)
UniverselleDes comptes, des groupes globaux et universels de toute la forêtForêts à plusieurs domaines

AGDLP : les comptes (Accounts) vont dans des groupes Globaux, mis dans des groupes de Domaine Local, qui reçoivent les Permissions. Dans un petit lab, on donne souvent les droits directement aux groupes globaux (c'est ce que fait le TP) ; AGDLP prend tout son sens quand plusieurs services partagent les mêmes ressources.

Source : Microsoft Learn — Active Directory security groups · Microsoft Learn — Delegating administration of account OUs and resource OUs

Exemple travaillé

Accueillir Sacha Somers dans le service Development

  1. Étape 1 · le besoin

    Un compte, un accès, un collègue qui gère le service

    Sacha arrive. Il doit ouvrir une session, accéder aux ressources du service Development, et jsmith doit pouvoir créer les comptes de ce service sans devenir administrateur du domaine.

  2. Étape 2 · le rangement

    L'OU pour l'endroit, le groupe pour le droit

    Le compte vit dans l'OU Development, elle-même sous ORION-DPT : l'annuaire reproduit l'organisation. Les droits, eux, ne vont pas à Sacha mais au groupe global DEV-GRP (personnes regroupées par fonction) : Sacha n'a qu'à en être membre.

    Une tâche, une OU, pas le domaine

    Sur l'OU Development, on délègue à jsmith la tâche « Create, delete, and manage user accounts ». Il gère les comptes de cette OU, et rien d'autre.

Voir la solution

Voir la démarche et la cause

Démarche : le compte existe et il est bien rangé : le problème n'est ni l'OU ni le groupe, mais l'état du compte. Cause : le mot de passe a été refusé par la stratégie (trop court ou pas assez complexe) ; New-ADUser a signalé l'erreur mais créé quand même le compte, désactivé (un compte créé sans -Enabled $true reste aussi désactivé). Correctif : lui donner un mot de passe conforme avec Set-ADAccountPassword -Reset, puis Enable-ADAccount.

À retenir

  • L'OU range selon l'organisation ; le groupe porte les droits. On ne donne jamais un droit à une personne.
  • AGDLP : comptes, groupes globaux, groupes de domaine local, permissions. Un groupe global regroupe des personnes, un groupe de domaine local porte des droits sur une ressource.
  • Un utilisateur modèle désactivé crée des comptes cohérents ; la délégation sur une OU confie une tâche sans donner le domaine.
  • Un compte créé avec une erreur de mot de passe est désactivé : Set-ADAccountPassword -Reset, puis Enable-ADAccount.

DNS en pratique

Le principe du DNS est expliqué dans Réseau : les bases. Sur Windows Server, il s'agit de créer les zones, les enregistrements, de régler les redirecteurs, et de savoir lire le cache quand un changement « ne prend pas ».

Ce que tu sauras faire

  • Choisir le type de zone (primaire, secondaire, intégrée à AD) selon le besoin.
  • Créer la zone inverse, un enregistrement A avec son PTR, un alias CNAME et un redirecteur.
  • Expliquer pourquoi un changement DNS « ne prend pas » (cache, TTL) et vider le cache au bon endroit.

Avant de commencer : chapitre Installer Active Directory et le principe du DNS dans Réseau : les bases · 35 min · SRV-AD01 et un poste CLIENT-WIN11 du lab.

Des noms pour les humains, et pour Active Directory

Les machines se joignent par adresse, les personnes par nom. Dans un domaine, le DNS fait plus : c'est lui qui permet à un poste de retrouver son contrôleur de domaine. Sans zone correcte, un serveur déplacé ou renuméroté devient introuvable, et le poste ne joint plus le domaine.

Un cas courant : on change l'adresse d'un serveur, le serveur DNS répond la nouvelle, et un poste continue d'utiliser l'ancienne. Savoir où vit la donnée (zone, serveur, cache du poste) évite de chercher au mauvais endroit.

Zones, enregistrements et cache

Une zone est la partie de l'espace de noms dont un serveur détient les enregistrements. La zone directe (orion.local) traduit un nom en adresse (enregistrement A) ; la zone inverse traduit une adresse en nom grâce aux enregistrements PTR ; un CNAME est un alias vers un autre nom. Le type de zone dit où vivent les données :

Type de zoneOù vivent les donnéesQuand
PrimaireUn fichier sur ce serveur, modifiableDNS autonome (le TP DNS du cours, sans AD)
SecondaireUne copie en lecture seule, transférée depuis le primaireRedondance hors AD
Intégrée à ADDans l'annuaire, répliquée avec lui sur tous les DCDès qu'il y a un domaine AD DS : le DNS y est intégré

Le redirecteur est la seule porte du lab vers les noms d'Internet : les postes interrogent le DC, qui répond pour orion.local et transfère tout le reste. C'est ce qui permet aux postes de n'avoir que le DNS des DC tout en naviguant.

Enfin, chaque réponse DNS porte un TTL : la durée pendant laquelle le poste (et un serveur intermédiaire) peut la garder en cache au lieu de reposer la question. Tant que le TTL n'est pas écoulé, la modification faite sur le serveur n'est pas vue du poste.

Source : Microsoft Learn — DNS Server overview · Microsoft Learn — Add-DnsServerForwarder

Exemple travaillé

Publier srv-web01 et l'alias storage

  1. Étape 1 · le besoin

    Deux noms pour les postes : un serveur, un alias

    Les postes doivent joindre srv-web01.orion.local par son nom, retrouver ce nom à partir de 172.16.50.25, et utiliser storage comme second nom de SRV-FILE01.

  2. Étape 2 · les choix

    Zone intégrée, A avec PTR, CNAME pour l'alias

    Le domaine AD existe, donc la zone orion.local est intégrée à AD. Le PTR a besoin d'une zone inverse, créée pour 172.16.50.0/24, et se crée en même temps que l'A (-CreatePtr). Pour storage, un CNAME vers srv-file01.orion.local plutôt qu'un second A : si l'adresse de SRV-FILE01 change, un seul enregistrement est à corriger.

  3. Étape 3 · la vérification

    Trois nslookup depuis le poste

    On résout le nom, l'adresse et l'alias depuis CLIENT-WIN11. Si une réponse montre l'ancienne valeur après un changement, on regarde le TTL et le cache avant de toucher au serveur.

    Zone, PTR et alias sont posés une fois ; le reste du temps, le DNS se vérifie, il ne se refait pas.

PowerShell — SRV-AD01 : zone inverse, enregistrements, redirecteur
Add-DnsServerPrimaryZone -NetworkId "172.16.50.0/24" -ReplicationScope Forest      # zone inverse
Add-DnsServerResourceRecordA -ZoneName orion.local -Name srv-web01 -IPv4Address 172.16.50.25 -CreatePtr
Add-DnsServerResourceRecordCName -ZoneName orion.local -Name storage -HostNameAlias srv-file01.orion.local
Add-DnsServerForwarder -IPAddress 1.1.1.1                                           # le reste du monde

Le cache, ou pourquoi un changement « ne prend pas »

Le TP final demande de modifier un enregistrement et d'observer le cache : le poste continue d'utiliser l'ancienne réponse jusqu'à la fin de son TTL. Pour voir et vider : ipconfig /displaydns, ipconfig /flushdns (ou Clear-DnsClientCache) côté poste ; Clear-DnsServerCache côté serveur.

Vérifier

Résolution directe, inverse et alias.

Invite de commandes — CLIENT-WIN11

nslookup 172.16.50.25
nslookup storage.orion.local

Sortie attendue

Address:  172.16.50.20
Aliases:  storage.orion.local

La résolution inverse échoue (Nonexistent domain) : la zone inverse manque, ou l'enregistrement A a été créé sans -CreatePtr (case « Create associated PTR record » dans la console).

À toi — un second nom pour SRV-FILE01

Les utilisateurs veulent joindre SRV-FILE01 sous le nom partage, sans nouvelle adresse. Ajoute-le dans la zone orion.local : énoncé seul, écris la commande.

Voir la solution
PowerShell — SRV-AD01
Add-DnsServerResourceRecordCName -ZoneName orion.local -Name partage -HostNameAlias srv-file01.orion.local

reconstitué, non testé : c'est la commande de l'alias storage du module, avec un autre nom. Un CNAME pointe vers un nom, jamais vers une adresse.

Variante sans indice

Avant de tester une modification d'enregistrement, tu veux repartir d'un cache propre : nomme les commandes à lancer sur le poste, puis sur le serveur DNS.

Voir la solution

Sur le poste : ipconfig /flushdns (ou Clear-DnsClientCache) ; ipconfig /displaydns permet de voir ce qui est en cache. Sur le serveur : Clear-DnsServerCache.

Quand ça casse — le nom se résout, l'adresse non

Depuis CLIENT-WIN11, nslookup srv-web01.orion.local renvoie bien 172.16.50.25. Mais nslookup 172.16.50.25 répond Nonexistent domain. Le serveur DNS ne signale aucune erreur.

Voir la démarche et la cause

Démarche : la résolution directe marche, seule l'inverse échoue : on regarde donc la zone inverse et les PTR, pas la zone orion.local. Cause : la zone inverse manque, ou l'enregistrement A a été créé sans -CreatePtr (case « Create associated PTR record » dans la console). Correctif : créer la zone inverse 172.16.50.0/24 si elle manque, puis recréer l'A avec son PTR.

Question éclair

Tu passes l'enregistrement A de srv-web01 de .25 à .26. Sur le client, nslookup srv-web01.orion.local répond bien .26, mais ping srv-web01 vise toujours .25. Pourquoi ?

nslookup interroge directement le serveur DNS et ignore le cache du poste ; ping passe par le client DNS de Windows, qui réutilise la réponse en cache. ipconfig /displaydns le montre, ipconfig /flushdns (ou Clear-DnsClientCache) règle le problème tout de suite.

À retenir

  • Zone intégrée à AD dès qu'il y a un domaine ; zone inverse pour les PTR ; CNAME pour les alias ; redirecteur pour le reste du monde.
  • Les postes n'ont que le DNS des DC : le DC répond pour orion.local et transfère le reste au redirecteur.
  • Un changement qui « ne prend pas » est souvent un cache jusqu'à la fin du TTL : ipconfig /flushdns côté poste, Clear-DnsServerCache côté serveur.
  • nslookup interroge le serveur, ping passe par le cache du poste : leurs réponses peuvent différer.

DHCP en pratique

DORA, les baux et les options sont expliqués dans Réseau : les bases. Côté Windows Server, deux étapes qu'on oublie : terminer la configuration post-installation, et autoriser le serveur dans Active Directory — un DHCP non autorisé ne distribue rien.

Ce que tu sauras faire

  • Installer le rôle DHCP, terminer sa configuration et l'autoriser dans Active Directory.
  • Créer une étendue avec ses options (passerelle, DNS, domaine) et une réservation.
  • Diagnostiquer un client sans bail (adresse en 169.254) ou qui reçoit un mauvais DNS.

Avant de commencer : chapitres Installer Active Directory et DNS en pratique, et Réseau : les bases pour DORA · 35 min · SRV-AD01 et CLIENT-WIN11 sur le commutateur LABOPS.

Distribuer les réglages réseau, sans les saisir à la main

Sans DHCP, chaque poste se règle à la main : adresse, masque, passerelle, DNS. Un oubli et le poste ne joint plus rien. Le DHCP donne tout cela au démarrage, depuis un seul endroit, et on peut corriger un réglage pour tout un réseau d'un coup.

Ce point unique est aussi le risque : une option fausse se retrouve sur tous les postes. Dans Orion, une seule option DNS erronée suffit à rendre le domaine introuvable alors que chaque poste a bien son adresse.

Autorisation, étendue, options et réservation

Un serveur DHCP Windows dans un domaine doit d'abord être autorisé : son inscription dans Active Directory empêche des serveurs non autorisés de distribuer des adresses aux clients. Sans elle, il ne distribue rien. Une fois autorisé, il distribue ce qu'on lui a décrit :

ÉlémentIl décritDans le lab Orion
ÉtendueLa plage d'adresses distribuées sur un réseauLAN-ORION : de 172.16.50.100 à 172.16.50.199, masque 255.255.255.0
Option 3La passerelle par défaut172.16.50.1
Option 6Les serveurs DNS : les contrôleurs de domaine172.16.50.10 et 172.16.50.11
Option 15Le nom de domaineorion.local
RéservationUne même adresse pour une MAC donnée (imprimante, borne)172.16.50.150 pour IMP-01

Un client qui n'obtient aucun bail finit en 169.254.x.x (adresse que Windows se donne lui-même). Un client qui obtient un bail avec une mauvaise option 6 a une adresse, mais ne trouve pas son domaine.

Le serveur de fichiers : partages et droits NTFS

Le TP final pose des contraintes précises : un dossier par service, chacun accessible à son seul groupe en lecture et écriture, un dossier Public pour tous, sans aucun Deny et en s'appuyant sur l'héritage. Deux couches de droits s'appliquent : celles du partage et celles du système de fichiers (NTFS).

Ce que tu sauras faire

  • Calculer le droit effectif d'un accès par le réseau à partir du droit de partage et du droit NTFS.
  • Poser les droits d'un dossier de service avec icacls : couper l'héritage en copiant, donner Modify au groupe, retirer Users.
  • Justifier l'absence de Deny et expliquer un refus qui suit un ajout de groupe.

Avant de commencer : chapitre Organiser l'annuaire pour les groupes (DEV-GRP, ACC-GRP) · 40 min · SRV-FILE01 (172.16.50.20) joint au domaine, SRV-AD01 allumé.

Donner à chaque service ses dossiers, et rien de plus

Un service ne doit voir que ses propres dossiers : la comptabilité ne lit pas ceux du développement. Quand on donne des droits « au cas où », au fil des demandes, le serveur finit ouvert à tout le monde, ou bien un blocage posé trop vite touche quelqu'un qu'on n'avait pas prévu.

Dans Orion, SRV-FILE01 héberge D:\DEPARTMENTS : un dossier par service, un groupe par service. La méthode est toujours la même (un partage large, des droits fins sur le dossier, donnés à des groupes), et elle se vérifie en quelques commandes.

Partage, NTFS, héritage et jeton

Un partage publie un dossier sur le réseau (protocole SMB). Les droits NTFS sont portés par le dossier lui-même, sous forme d'une liste d'entrées de contrôle d'accès : une entrée associe un utilisateur ou un groupe à un droit. Un dossier reçoit par défaut les entrées de son parent : c'est l'héritage. Quand un utilisateur ouvre une session, Windows construit son jeton d'accès, qui contient l'identité de l'utilisateur et celle de tous ses groupes ; c'est avec ce jeton que chaque droit est comparé.

Le droit effectif

Pour un accès par le réseau, Windows calcule le droit du partage et le droit NTFS séparément, puis applique le plus restrictif des deux. Pratique courante : partage large (Change pour les utilisateurs du domaine), droits fins en NTFS. Le calcul détaillé, avec exercices, est dans le module Stockage & clustering.

Pourquoi « pas de Deny »

Un Deny explicite l'emporte sur tout Allow et se propage aux sous-dossiers par héritage (seul un Allow explicite bat un Deny hérité) : il finit par bloquer quelqu'un qu'on n'avait pas prévu (un admin membre du mauvais groupe). Il suffit de ne pas accorder : sans permission, pas d'accès.

Exemple travaillé

Le dossier Development, du besoin au droit effectif

  1. Étape 1 · le besoin

    Development pour DEV-GRP seulement

    Les membres de DEV-GRP lisent et écrivent dans D:\DEPARTMENTS\Development. Personne d'autre n'y accède, et on s'interdit tout Deny.

  2. Étape 2 · le raisonnement

    Un partage large, un NTFS précis

    Le partage DEPARTMENTS donne Change à Domain Users : il laisse passer tout le monde, sans rien décider. Le tri se fait en NTFS : on coupe l'héritage en gardant une copie (/inheritancelevel:d), on donne Modify à DEV-GRP en (OI)(CI), on donne à CREATOR OWNER le contrôle total sur ce qu'il crée ((IO)), puis on retire Users et Authenticated Users, que la copie avait conservés.

  3. Étape 3 · le calcul

    Trois personnes, trois droits effectifs

    Un membre de DEV-GRP : Change au partage, Modify en NTFS, donc il modifie. Un utilisateur d'un autre service : Change au partage, mais aucune entrée NTFS pour lui, donc rien. Un administrateur : il passe par BUILTIN\Administrators, contrôle total.

    C'est le droit NTFS, pas le partage, qui décide de qui entre.

Question éclair

À 10 h, tu ajoutes sso au groupe DEV-GRP. À 10 h 05, toujours connecté depuis 8 h, il est refusé sur \\SRV-FILE01\DEPARTMENTS\Development. Que lui dis-tu ?

Les groupes d'un utilisateur sont lus à l'ouverture de session et placés dans son jeton (et son ticket Kerberos). Tant qu'il ne se reconnecte pas, il garde la liste de 8 h. whoami /groups sur le poste montre les groupes du jeton actuel.

À retenir

  • Partage large, NTFS précis, droit effectif = le plus restrictif des deux.
  • Couper l'héritage avec copie (/inheritancelevel:d), donner aux groupes, retirer Users, jamais de Deny.
  • Un changement de groupe ne compte qu'après une nouvelle ouverture de session (le jeton est ancien).

DFS Namespace

Le TP DFS du cours part d'un problème réel : les utilisateurs accèdent à \\SRV-FILE01\DEPARTMENTS, et le jour où le serveur change de nom, tous les raccourcis cassent. Un espace de noms DFS leur donne un chemin qui ne dépend d'aucun serveur : \\orion.local\shares.

Ce que tu sauras faire

  • Distinguer DFS-N de DFS-R et dire ce que chacun apporte.
  • Créer un espace de noms basé sur le domaine et un dossier DFS qui pointe vers un partage réel.
  • Vérifier le chemin unique depuis un client et dire où se règlent les droits.

Avant de commencer : chapitres Le serveur de fichiers et DNS en pratique · 30 min · SRV-FILE01 (172.16.50.20) avec ses dossiers, CLIENT-WIN11 qui utilise le DNS du domaine.

Un chemin qui survit au changement de serveur

Quand des dizaines de raccourcis, de lecteurs réseau et de documents contiennent \\SRV-FILE01\DEPARTMENTS, remplacer ou renommer ce serveur oblige à tout corriger. Le coût vient du fait que le chemin porte le nom d'une machine.

Dans Orion, un espace de noms DFS donne à tous le même chemin, \\orion.local\shares, et c'est lui qui sait quel partage réel se cache derrière. On change la cible, pas les raccourcis.

Espace de noms, cible et réplication

Namespace (DFS-N)

Un chemin logique unique ; chaque dossier pointe vers un ou plusieurs partages réels (cibles). On peut déplacer un partage sans changer ce que voient les utilisateurs. C'est ce que fait le TP.

Réplication (DFS-R)

Synchronise le contenu de dossiers entre serveurs. Combinée à plusieurs cibles, elle donne de la tolérance de panne. Le TP l'exclut volontairement.

Un espace de noms a une racine (\\orion.local\shares), qui contient des dossiers ; chaque dossier a une ou plusieurs cibles, c'est-à-dire des partages réels. Il existe deux types d'espace de noms :

TypeCheminÀ retenir
Basé sur le domaine (Domain-based)\\orion.local\sharesLe nom est celui du domaine : il ne dépend d'aucun serveur. C'est le choix du TP (DomainV2).
Autonome (Stand-alone)\\SRV-FILE01\sharesLe nom contient celui du serveur : on retrouve le problème d'origine.

DFS n'ajoute aucun droit : les droits d'accès restent ceux des partages et des dossiers cibles, réglés comme au chapitre précédent.

Les stratégies de groupe (GPO)

Les GPO appliquent des réglages à des milliers de postes et d'utilisateurs depuis un seul endroit : sécurité, lecteurs réseau, fond d'écran, restrictions. Le TP final en demande quatre ; ce chapitre explique comment elles s'appliquent, et comment vérifier qu'elles le font.

Ce que tu sauras faire

  • Prédire quelle GPO l'emporte selon l'ordre L-S-D-OU, Enforced et Block Inheritance.
  • Créer une GPO et la lier à l'OU qui contient les bons objets, utilisateurs ou ordinateurs.
  • Vérifier ce qui s'applique réellement avec gpupdate et gpresult.

Avant de commencer : chapitres Organiser l'annuaire (les OU) et DNS en pratique (le poste doit joindre un DC) · 40 min · SRV-AD01, CLIENT-WIN11 joint au domaine, l'OU ORION-DPT.

Régler mille postes depuis un seul endroit

Interdire le Panneau de configuration, fixer un fond d'écran ou une longueur de mot de passe poste par poste ne tient pas à l'échelle, et personne ne sait ensuite ce qui est réellement appliqué. Une stratégie de groupe décrit le réglage une fois, et les machines et utilisateurs visés le reçoivent.

Le revers est qu'une GPO mal placée ne fait rien, ou fait tout autre chose que prévu, sans message d'erreur. Savoir où elle est liée et quelle autre la contredit est la moitié du métier.

Une GPO est d'abord un objet de l'annuaire, avec deux parties : Computer et User. Elle ne s'applique à personne tant qu'elle n'est pas liée à un site, au domaine ou à une OU : c'est le lien qui la fait agir sur les objets situés dessous.

Où et dans quel ordre

Une GPO est un objet de l'annuaire qu'on lie à un site, au domaine ou à une OU. Elle s'applique aux utilisateurs et ordinateurs contenus dans ce conteneur, dans l'ordre L-S-D-OU : locale, site, domaine, puis OU de la plus haute à la plus proche. En cas de conflit, la dernière appliquée gagne — donc l'OU la plus proche.

Avec Enforced, la GPO du domaine gagne même contre une GPO plus proche : le Panneau de configuration est interdit. Sans Enforced, l'ordre L-S-D-OU s'applique : la GPO de l'OU, appliquée en dernier, gagne et l'autorise.

Quand ça casse — le lecteur X: n'arrive pas pour un utilisateur

La GPO GPO_Drive_Map est liée à OU=ORION-DPT, où se trouve sso. Sur son poste, après gpupdate /force, il n'a pas de lecteur X:. gpresult /r /scope user range GPO_Drive_Map parmi les objets filtrés, alors que GPO_User_Restrictions s'applique bien.

Voir la démarche et la cause

Démarche : le lien est bon (la GPO est vue), donc ce n'est ni l'OU ni le DNS. Une GPO « filtrée » est écartée pour cet utilisateur : on ouvre le rapport complet (gpresult /h C:\Temp\rapport.html) pour lire la raison, puis le filtrage de sécurité de la GPO dans la console. Cause : le filtrage de sécurité (par défaut Authenticated Users) a été restreint à un groupe dont sso ne fait pas partie. Correctif : ajouter le groupe de sso (ou rétablir Authenticated Users) dans le filtrage, puis gpupdate /force et relire gpresult.

Question éclair

La GPO du lecteur X: (partie User) est liée à l'OU Postes, qui ne contient que les comptes ordinateurs. Les utilisateurs sont dans ORION-DPT. Ils n'ont pas de X:. Que fais-tu ?

La partie User d'une GPO s'applique aux utilisateurs situés sous son lien, la partie Computer aux ordinateurs. New-GPLink -Name "GPO_Drive_Map" -Target "OU=ORION-DPT,DC=orion,DC=local", puis gpresult /r /scope user sur le client. (Le loopback permet l'inverse, mais c'est un cas particulier.)

À retenir

  • Une GPO s'applique par son lien, dans l'ordre local, site, domaine, OU, la plus proche gagnant ; Enforced et Block Inheritance sont les exceptions.
  • Les réglages User visent des utilisateurs, Computer des machines : on lie l'objet à l'OU qui contient les bons comptes.
  • gpupdate /force puis gpresult /r (ou /h) disent ce qui s'applique vraiment, et ce qui est filtré.

Sécuriser les comptes et le serveur

La gestion des comptes est la première ligne de défense d'un domaine : qui peut se connecter, avec quels privilèges, et ce qu'on garde comme trace. Ce chapitre reprend les notes de sécurité du cours.

Ce que tu sauras faire

  • Placer une politique de mots de passe là où elle vaut pour les comptes du domaine, et dire quand utiliser une stratégie affinée.
  • Nommer les mesures de protection des comptes (comptes séparés, LAPS, moindre privilège) et ce que chacune empêche.
  • Repérer dans le journal Security les événements 4625, 4740 et 4728.

Avant de commencer : chapitres Les stratégies de groupe et Organiser l'annuaire · 35 min · SRV-AD01 et CLIENT-WIN11, un compte standard et un compte d'administration.

Les comptes, première cible d'une attaque

Un attaquant n'a pas besoin de casser un serveur s'il obtient un mot de passe : un compte deviné, un administrateur qui lit un mail piégé, un mot de passe local identique sur toutes les machines. Dans un domaine, un seul compte privilégié compromis ouvre tout le reste.

La défense a deux volets : limiter ce qu'un compte peut faire s'il est volé, et garder assez de traces pour voir une tentative. Orion applique les deux sur ses contrôleurs de domaine et ses postes.

À toi — exiger plus pour les administrateurs

Les mots de passe des comptes du domaine doivent faire 12 caractères minimum, mais ceux du groupe des administrateurs du domaine 16. Où poses-tu chaque règle, et avec quoi ?

Voir la solution

La règle générale va dans la Default Domain Policy, liée au domaine : c'est la seule politique de mots de passe qui vaut pour les comptes du domaine. L'exigence plus forte pour un groupe précis passe par une stratégie de mots de passe affinée, créée avec New-ADFineGrainedPasswordPolicy et attachée au groupe. Une GPO liée à une OU ne ferait rien pour ces comptes.

Variante sans indice

Un collègue a mis une GPO « mots de passe de 14 caractères » sur l'OU des serveurs. Sacha, compte du domaine, peut pourtant encore choisir un mot de passe de 8 caractères. Explique pourquoi et dis ce qu'il faut faire.

Voir la solution

Une politique de mots de passe liée à une OU ne s'applique qu'aux comptes locaux des ordinateurs de cette OU, pas aux comptes du domaine. Pour tous les comptes du domaine, on modifie la Default Domain Policy ; pour un groupe précis, on crée une stratégie affinée.

Quand ça casse — un seul mot de passe ouvre tous les postes (scénario fictif)

Le mot de passe de l'administrateur local d'un poste du lab est découvert. En quelques heures, le même compte ouvre une session sur plusieurs autres postes et serveurs : le journal Security montre des 4624 successifs sur des machines différentes pour ce compte local. Tous les postes viennent de la même image.

Voir la démarche et la cause

Démarche : un même compte local qui réussit partout n'est pas une série d'attaques indépendantes : le mot de passe est le même sur toutes les machines. Cause : l'administrateur local a le même mot de passe partout, ce qui permet le mouvement latéral d'une machine à l'autre. Correctif : Windows LAPS, qui donne à chaque machine un mot de passe d'administrateur local unique, stocké dans AD et renouvelé seul (Update-LapsADSchema puis une GPO), et la séparation des comptes d'administration.

Piège

Une politique de mots de passe placée dans une GPO liée à une OU ne change rien pour les comptes du domaine : elle ne s'applique qu'aux comptes locaux des ordinateurs de cette OU. Pour les comptes du domaine, une seule politique : celle liée au domaine (Default Domain Policy). Pour exiger plus d'un groupe précis (les administrateurs), on utilise une stratégie de mots de passe affinée (FGPP, New-ADFineGrainedPasswordPolicy).

À retenir

  • Politique de mots de passe et de verrouillage dans la Default Domain Policy ; une stratégie affinée (FGPP) pour un groupe précis.
  • Comptes d'administration séparés, LAPS pour les administrateurs locaux, moindre privilège.
  • Journal Security : 4625 en rafale (force brute), 4740 sur le DC (verrouillage), 4728 (ajout à un groupe global).

Dépanner Active Directory

Presque toutes les pannes d'AD tombent dans trois familles : le DNS, l'heure et la réplication. Ces commandes les isolent en quelques minutes.

Ce que tu sauras faire

  • Classer une panne d'Active Directory dans l'une des trois familles : DNS, heure ou réplication.
  • Choisir la commande qui isole la cause : nltest, w32tm, repadmin, dcdiag, Test-ComputerSecureChannel.
  • Raconter ce qui se passe à l'ouverture d'une session de domaine, du DNS au jeton d'accès, pour savoir à quelle étape une panne se situe.

Avant de commencer : chapitres Le second contrôleur de domaine (la réplication), DNS en pratique et Les stratégies de groupe · 40 min · SRV-AD01, SRV-AD02 et CLIENT-WIN11 joint au domaine.

Une panne d'AD se dépanne par familles, pas au hasard

Un utilisateur qui ne peut plus ouvrir de session, un compte créé qui n'apparaît pas sur l'autre contrôleur, une GPO qui ne s'applique pas : trois symptômes très différents, et pourtant la cause est presque toujours la même petite poignée. Tester au hasard coûte une heure ; tester dans le bon ordre en coûte cinq minutes.

Ce chapitre ne t'apprend pas de nouvelles briques : il te donne la carte des pannes et les commandes qui permettent de trancher, du poste jusqu'au contrôleur de domaine.

Les trois familles, et la commande de chacune

Trois mécanismes font tenir un domaine, et chacun a sa panne type. Le DNS permet au poste de trouver un contrôleur, grâce aux enregistrements SRV. L'heure permet à Kerberos de l'authentifier : un ticket porte un horodatage, et un écart de plus de 5 minutes le fait refuser. La réplication fait que tous les contrôleurs partagent les mêmes données, annuaire et SYSVOL. Un poste dont le canal sécurisé avec le domaine est rompu (le mot de passe de son compte machine ne correspond plus) forme un quatrième cas, à part.

Pas à pas

Ce qui se passe quand sso ouvre une session sur CLIENT-WIN11

  1. Étape 1 · CLIENT-WIN11 → DNS (SRV-AD01)

    Trouver un contrôleur de domaine

    Le poste demande au DNS les enregistrements SRV du domaine, par exemple _ldap._tcp.dc._msdcs.orion.local. Réponse : SRV-AD01 et SRV-AD02, avec leurs adresses.

    Sans le DNS du domaine, tout s'arrête ici : enregistrements SRV, testés par nltest /dsgetdc:orion.local.

  2. Étape 2 · CLIENT-WIN11 → SRV-AD01 (LDAP, 389)

    Choisir le DC qui répond

    Le poste envoie une courte requête LDAP (le « ping LDAP ») aux DC trouvés et garde le premier qui répond, de préférence dans son site.

    Le poste a choisi son DC pour la suite de la session.

  3. Étape 3 · CLIENT-WIN11 → KDC de SRV-AD01 (Kerberos, 88)

    AS-REQ / AS-REP : obtenir le TGT

    Le poste envoie un horodatage chiffré avec une clé tirée du mot de passe de sso : le mot de passe ne circule jamais. Le DC le déchiffre, vérifie l'heure, et renvoie un TGT (Ticket Granting Ticket), le « laissez-passer » valable 10 heures par défaut.

    Écart d'heure de plus de 5 minutes ou mauvais mot de passe : refus ici. C'est pourquoi l'heure fait partie du trio de dépannage.

  4. Étape 4 · CLIENT-WIN11 → KDC (TGS-REQ / TGS-REP)

    Échanger le TGT contre des tickets de service

    Pour chaque service dont il a besoin (le poste lui-même, LDAP et SMB du DC…), le poste présente le TGT et reçoit un ticket de service. Chaque ticket porte les groupes de l'utilisateur, lus à ce moment-là.

    Un ticket par service, sans redemander le mot de passe : c'est l'authentification unique. klist les affiche.

  5. Étape 5 · CLIENT-WIN11 (local)

    Construire le jeton d'accès

    Windows fabrique le jeton de la session : le SID de sso et ceux de tous ses groupes (DEV-GRP, Domain Users…). Toutes les vérifications de droits de la session s'appuieront sur ce jeton.

    Le jeton est figé : un groupe ajouté après cette étape ne compte qu'à la prochaine ouverture de session.

  6. Étape 6 · CLIENT-WIN11 → SRV-AD01 (LDAP 389, SMB 445)

    Appliquer les GPO utilisateur

    Le poste demande par LDAP la liste des GPO liées aux OU de sso (site, domaine, ORION-DPT…), puis lit leur contenu dans \\orion.local\SYSVOL. Les GPO Computer ont déjà été appliquées au démarrage du poste.

    Ordre L-S-D-OU ; port 445 bloqué ou SYSVOL non répliqué : la session s'ouvre, mais sans ses GPO.

  7. Étape 7 · CLIENT-WIN11 → SRV-FILE01 (SMB, 445)

    Ouvrir le lecteur X:

    La GPO monte X:. Le poste obtient un ticket de service pour SRV-FILE01 (étape 4) et le présente au serveur de fichiers, qui vérifie le partage puis le NTFS sans recontacter le DC pour le mot de passe.

    Droit effectif = le plus restrictif entre partage et NTFS, calculé avec les groupes du ticket.

Quand ça casse — plus aucune session sur un seul poste (scénario fictif)

Voir la démarche et la cause

Une VM qui était éteinte peut avoir une horloge décalée : on lit w32tm /query /status et on compare à l'heure du DC. Cause : l'écart d'heure dépasse 5 minutes, et Kerberos refuse l'authentification (étape 3 du pas à pas). Correctif : resynchroniser l'heure du poste (w32tm /resync) puis relancer l'ouverture de session. Si le message avait parlé de relation d'approbation, on serait passé à Test-ComputerSecureChannel -Repair.

Question éclair

Une VM poste, restaurée d'un point de contrôle d'il y a trois semaines, refuse toute ouverture de session : « la relation d'approbation entre cette station de travail et le domaine principal a échoué ». Quelle commande lances-tu (en administrateur local) ?

Un poste change le mot de passe de son compte machine tous les 30 jours par défaut. Le point de contrôle a remis un ancien mot de passe, que le DC ne reconnaît plus. Test-ComputerSecureChannel renvoie False ; avec -Repair et un compte autorisé, il réinitialise le canal entre le poste et son domaine, sans sortir du domaine.

À retenir

  • Pour AD, toujours dans cet ordre : le DNS (nltest, SRV), l'heure (w32tm), la réplication (repadmin), puis dcdiag. Les trois premières causes représentent l'immense majorité des pannes.
  • Kerberos refuse un écart d'heure de plus de 5 minutes ; un canal sécurisé rompu se répare avec Test-ComputerSecureChannel -Repair.
  • Un pare-feu qui bloque une partie des ports donne des pannes « à moitié » : jonction qui marche, GPO ou réplication qui échouent.

À toi — l'ordre de montée

Un collègue propose d'installer DHCP et de créer les GPO avant de promouvoir SRV-AD02. Que lui réponds-tu ?

Voir la solution

L'ordre n'est pas interdit pour DHCP, mais il fait perdre la preuve : on veut d'abord un second contrôleur qui réplique (repadmin /replsummary), car DHCP autorisé et GPO écrivent dans l'annuaire et se retrouveraient sur un seul DC. Le tableau des dépendances donne l'ordre qui garde chaque preuve utile.

Variante sans indice

Le client obtient bien une adresse, mais nltest /dsgetdc:orion.local échoue. Dans quel ordre vérifies-tu les briques, et laquelle suspectes-tu en premier ?

Voir la solution

On part du client : ipconfig /all pour lire le DNS reçu, puis Resolve-DnsName vers le contrôleur de domaine, puis nltest. La première suspecte est l'option DNS de l'étendue DHCP : le bail est correct, mais le DNS distribué ne connaît pas orion.local.

Quand ça casse — le client a une adresse mais ne trouve pas le domaine

Après la montée du lab, CLIENT-WIN11 obtient une adresse de l'étendue .100–.199, mais refuse toute ouverture de session de domaine. Get-ADDomain et repadmin /replsummary sont corrects sur les contrôleurs.

Voir la démarche et la cause

Démarche : les contrôleurs vont bien, le client a une adresse : le défaut est entre les deux. ipconfig /all sur le client montre le DNS reçu. Cause probable : l'option DNS de l'étendue DHCP pointe vers la passerelle (172.16.50.1) au lieu des contrôleurs, comme dans le chapitre DHCP. Correctif : Set-DhcpServerv4OptionValue -ScopeId 172.16.50.0 -DnsServer 172.16.50.10,172.16.50.11, puis ipconfig /renew et nltest /dsgetdc:orion.local sur le client.
